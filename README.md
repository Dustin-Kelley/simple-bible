# Simple Bible

Simple Bible is a production showcase of the [YouVersion React Native (Expo) SDK](https://developers.youversion.com/sdks/react-native-expo/quick-start) **2.1.0** on **Expo SDK 57** (React Native 0.86). The YouVersion packages are `@youversion/platform-react-native-expo-ui` and `@youversion/platform-react-native-expo-core`. Bible text is loaded from YouVersion. The app needs a network connection and a YouVersion App Key. It does not ship a bundled Bible, and it does not include its own search index.

Reading works without an account. Sign-in with YouVersion is optional. The SDK starts a PKCE flow whose redirect is `simplebible://callback`, as described in the [authentication guide](https://developers.youversion.com/sdks/react-native-expo/authentication). When sign-in finishes, `src/app/callback.tsx` sends you back to the Home, Read, and Settings tabs.

The SDK uses native modules. It does not run in Expo Go. Use a [development build](https://docs.expo.dev/develop/development-builds/introduction/).

## What you can do in the app

- Home shows the YouVersion verse of the day, your last reading position, and verses you saved.
- Read uses the SDK `BibleReader`, including chapter and version pickers.
- Settings changes the theme and signs you in or out of YouVersion.
- Share uses the device share sheet.

`BibleReader` and `VerseOfTheDay` show each Bible version's copyright line. Keep that attribution visible.

## Setup

Requirements: Node.js 22.13+, npm, Expo SDK 57, and an Expo account. iOS device builds need a Mac or EAS. Android device builds need the Android SDK or EAS. An existing Expo SDK 56 dev client will not run this app. Install a new development build after pulling.

```bash
npm install
cp .env.example .env.local
```

Put your App Key in `.env.local`:

```bash
EXPO_PUBLIC_YOUVERSION_APP_KEY=your_app_key
```

Get a free key at [platform.youversion.com](https://platform.youversion.com/). Restart Metro after you change it. The real key stays out of git.

In the YouVersion Platform console, register this callback URI for that key:

```text
simplebible://callback
```

That value is `AUTH_REDIRECT_URI` in `src/lib/youversion.ts`. It must match the `scheme` in `app.json` (`simplebible`) plus `://callback`. Register it in the YouVersion console. The matching screen is `src/app/callback.tsx`. It lives outside the tabs, on a root stack, and returns to the tab you left. If the app was opened from the redirect and there is nothing to go back to, it opens Home.

## Run

Web is only a layout check. Scripture and sign-in need a development build.

```bash
npm run web
# or: npx expo start --web --port 8081
```

Development build on a device (installs the dev client, then loads JavaScript from Metro):

```bash
eas build --profile development --platform ios
eas build --profile development --platform android
npx expo start --dev-client
```

iOS Simulator build:

```bash
eas build --profile development-simulator --platform ios
```

On a machine with Xcode or the Android SDK you can build locally instead:

```bash
npx expo run:ios
npx expo run:android
```

Rebuild the dev client after any native module change. A JavaScript reload is not enough.

## Store builds

Builds and submissions use [EAS](https://docs.expo.dev/build/introduction/). `ios/` and `android/` are generated by prebuild and are gitignored. `app.json` is the source of truth for the native project. The store version is `expo.version` in `app.json`. EAS stores the iOS build number and Android version code remotely and bumps them on production builds (`autoIncrement`).

Log in once:

```bash
npm install --global eas-cli
eas login
```

The App Key has to be present when EAS bundles the app. Create it in each EAS environment with visibility `sensitive`. A `secret` value is available on the EAS Build worker, so a production build can inline it. You cannot pull a secret down with `eas env:pull`, and on SDK 55 and later you cannot use a secret when bundling JavaScript for `eas update`. `sensitive` is the visibility that works for local development, store builds, and updates. The key is still embedded in the app either way.

```bash
eas env:set --name EXPO_PUBLIC_YOUVERSION_APP_KEY --value YOUR_KEY --environment development --visibility sensitive
eas env:set --name EXPO_PUBLIC_YOUVERSION_APP_KEY --value YOUR_KEY --environment preview --visibility sensitive
eas env:set --name EXPO_PUBLIC_YOUVERSION_APP_KEY --value YOUR_KEY --environment production --visibility sensitive
```

| Profile | What it produces |
| --- | --- |
| `development` | Dev client for a physical iPhone or Android device. Internal distribution. |
| `development-simulator` | Same dev client, built for the iOS Simulator. |
| `preview` | Release-like internal build. Android is an APK you can install directly. |
| `production` | Store build. Android is an AAB for Google Play. iOS is an IPA for App Store Connect. Build numbers auto-increment. |

```bash
eas build --platform ios --profile preview
eas build --platform android --profile preview

eas build --platform ios --profile production
eas build --platform android --profile production

eas submit --platform ios --profile production
eas submit --platform android --profile production
```

Build and hand the artifacts to submit in one step:

```bash
eas build --platform all --profile production --auto-submit
```

Android submit uploads to the Play internal testing track as a draft. It does not roll out to production. The steps Dustin still has to do by hand (Apple and Google credentials, store listing, callback registration) are in [docs/RELEASE.md](docs/RELEASE.md).

JavaScript-only fixes for a build already in the store, with the same native fingerprint:

```bash
eas update --channel production --environment production --message "Describe the change"
```

Use channel `preview` or `development` to target those builds. A native change, including a new native module, needs a new build. The App Key is baked in at bundle time, so changing it needs a new update or a new build.
